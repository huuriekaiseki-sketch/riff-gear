# 振り返り（品質ループのフィードバック化）

マージ済みPRに蓄積された構造化データ（PRテンプレートの3欄）とレビュー指摘を読み返し、**仕組みの側**（テンプレート・スキル・テスト・docs）を改善する提案を出す。個々のコードの振り返りではない。

判断基準は[品質ループと昇格基準](../../../docs/agents/quality-loop.md)を正本とする。**提案を出すこと自体が目的ではない**。昇格基準（繰り返し・影響大・判断ぶれの2つ以上）を満たさなければ「改善提案なし」と報告するのが正しい振り返いである。

## 手順

### 1. データ収集

1. `gh pr list --state merged --limit 10 --json number,title,body,mergedAt` で直近のマージ済みPRを取得する（件数を指定されたらそれに従う）
2. 前回の振り返り以降のPRに絞る（前回実施日はこのファイル末尾の「実施記録」を見る。初回は全件）
3. 各PRのレビューコメント・イシューでの指摘があれば `gh pr view <N> --comments` で補足する

### 2. 集計（3つの観点）

**観点A: 検証表の「対象外」「未実施」の頻発**
- テンプレート導入後のPRの検証表を横断し、項目ごとに 完了/一部完了/未実施/対象外 を数える
- 特定の項目がほぼ常に「対象外」なら、テンプレートの項目が実態に合っていない兆候。項目の削除・条件付き化を提案する
- 「未実施」が理由なしで繰り返されていたら、運用が守られていない兆候。原因（重すぎる/曖昧）を推定して提案する

**観点B: 「残る仕様上の制約」の再検討条件チェック**
- 各PRの制約欄から「制約 / 影響 / 受容判断または再検討条件」を抽出して一覧化する
- 再検討条件に**現時点で到達しているもの**がないか、コードベース・イシューの現状と突き合わせて判定する（例: 「票数が数千規模になったら」→ 実データ件数を確認）
- 到達していれば対応イシューの起票（または既存イシューの着手）を提案する。未到達なら一覧に「未到達」と明記するだけでよい

**観点C: 同種のハマり・指摘の繰り返し**
- 会話メモリ・known-failure-patterns.md・PRの経緯から、同じ種類のハマり（例: FK順序の削除ミス、int上限、TZ）が2回以上起きていないか探す
- 2〜3回起きていたら昇格候補（fixture化・ヘルパー化・skill追記・テスト追加）として提案する。1回なら記録の確認だけで提案しない

### 3. 提案と適用

1. 集計結果を「観点ごとの事実 → 提案（なしも可）」の形で開発者に報告する
2. 提案がある場合は**AskUserQuestionで承認を取ってから**適用する。勝手にルール・チェック項目を増やさない
3. 承認された変更は通常のPRフロー（ブランチ→PR→CI→マージ確認）で反映する

### 4. 実施記録の更新

このファイル末尾の実施記録に1行追記する（日付・対象PR範囲・提案数・適用数）。これが次回の「前回以降」の起点になる。
