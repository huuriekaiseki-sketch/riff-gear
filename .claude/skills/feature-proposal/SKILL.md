# 機能提案と組み込み

このskillは2段階で動く。**提案ゲート**（開発者にこの機能いる？と聞く）と、**6役割ワークフロー**（「いる」となった機能を確実に組み込む）。単発のサブエージェントに「組み込んで」と丸投げしない。

## 第1段階: 提案ゲート

1. 候補を集める。情報源は次の3つ:
   - `gh issue list --state open` のOPENイシュー
   - 直近のセッション・会話の流れ（例: 直前に作った機能の自然な拡張）
   - 自分の発案（既存機能の組み合わせ・EC定番機能でまだ無いもの）
2. 候補を2〜4個に絞り、**AskUserQuestionで「このプロダクトにこの機能は必要ですか？」を聞く**。各選択肢には「何ができるようになるか」と「規模感」を1行で添える。
3. 開発者の回答で分岐する:
   - **必要** → 第2段階へ。対応するイシューが無ければ起票してから進む
   - **いらない** → 実装しない。対応イシューがあれば、理由をコメントしてクローズするか提案する
   - **やっぱり外して**（既存機能の削除依頼）→ 削除も第2段階の6役割で行う（SweeperとFinderで影響範囲を洗ってから消す）

## 第2段階: 6役割ワークフロー

1人で順にこなすチェックリスト付きフェーズ。省略禁止。核は「**実装前に調査を強制する**」「**実装後に片付けを強制する**」の2点。

### Role 1: Sweeper（既存コード調査）

対象機能に関連する既存実装を機械的に洗い出す。

1. 機能のキーワードで `grep -rn` し、関連コードを一覧化する（`app/`, `lib/`, `supabase/migrations/`, `.env.local.example`）
2. ヒットしたファイルを全件読み、現状を把握する
3. **「実は既に実装済み」を必ず疑う**（過去にissue #9で発生: 実装済み機能が未実装として起票されていた）

出力: 「ファイルパス:行番号 — 現状」の箇条書き

### Role 2: Finder（関連イシュー・過去事例）

1. 機能キーワードを2〜3個抽出し、`gh issue list --state all --search "<keyword>"` と `gh pr list --state all --search "<keyword>"` で**CLOSED/MERGEDも含めて**検索する
2. 重複対応・既にクローズ済み・過去に見送られた経緯がないか確認する

出力: 「#番号 状態 タイトル — 関連度メモ」の箇条書き

### Role 3: Proposer（設計確認）

Sweeper・Finderの結果を踏まえ、実装方針を確認する。**このRoleは「内容についての質問に答えてもらうこと」と「仕様書を作って実装可否の承認を得ること」の2段階に分かれており、両方を完了するまでRole 4（Edit/Write）を開始しない。** 質問への回答（閾値・見た目・影響層など）が揃った時点で満足して実装に進むのは典型的な失敗パターンであり、それ自体は仕様確認の材料集めに過ぎず承認ではない。

**ステップA: 内容の確認（AskUserQuestion等）**

- 実装アプローチが複数あるなら選択肢として提示する（推奨に「(推奨)」を付ける）
- 閾値・文言・置き場所など、開発者の好みが出る設定値を確認する
- Sweeper/Finderで「既に実装済み」と判明した場合は、実装せず報告して終了する選択肢を必ず提示する
- **影響する層をAskUserQuestion（multiSelect）で確認する**: 「この機能はどの層に影響しますか？」→ UI（`app/`ページ・コンポーネント）／データ（`lib/`・Server Actions・Route Handlers）／DB（`supabase/migrations/`）。この回答がRole 4の実装方式を決める

**ステップB: 仕様書の作成と実装可否の承認（ステップAとは別の、独立した確認）**

ステップAの回答を材料に、**`docs/spec/<機能名>/SPEC.md`として仕様書ファイルを作成する**（口頭やチャットの要約だけで済ませない。ファイルとして残すことで、後から見返せる・レビューできる）。単なる質問の繰り返しではなく、「これから何を変更し、何を変更しないか」をまとまった文章として書き下す。

UI層が含まれる場合の作成手順（省略禁止。開発者は「文字だけの仕様だとUIのイメージが掴めない」という明確な課題感を持っており、これを飛ばして実装に進むと手戻りが発生する）:

1. **コード調査**: 対象のpage.tsx・actions.ts・呼び出しているRPC/Route Handlerを読む。スクリーンショットだけでは分からない、コードを読んで初めて分かる情報（どのServer Action/RPCが呼ばれるか、成功後に一覧を再取得するか、処理中にボタンを無効化しているか、失敗時のエラー内容、権限がない時の表示）を先に把握する
2. **現状を撮る**: 対象ページが既存なら`pr-screenshot`スキルの通常フロー（`capture-template.js`）でbefore画像を撮る。新規ページなら省略してよい。既存画面の変更なのにafterだけ、という状態にしない（[known-failure-patterns.md](../../../docs/agents/known-failure-patterns.md)の実例参照）
3. **変更後の画面案を作る**: `design`スキル（Claude Design canvas editor）で、既存ページの雰囲気を踏襲したモックを作る。**モックは仕様書本文（UI受入条件・状態設計）を書く前に作り、モックを見ながら本文を書く**（文章を先に書いて後からモックを足す順序にしない。文章先行だと配置・導線が文章に引きずられ、モックが「文章の挿絵」で終わる）
   - 見た目の変化だけなら静的モックでよく、`capture-mock-template.js`（ログイン・DB不要）でafter画像を撮る
   - **処理中表示・完了メッセージ・空表示・エラー表示など、操作で状態が変わるUXを含むなら、クリックで実際に動くモック**（`canvas.json`で`is_interactive: true`）にする。`pr-screenshot`スキルの`mock-capture.js`（`openMock()`）で状態ごとに撮り、下記「状態設計」表の該当行に画像を添える。作って終わりにせず、**実際にクリックして動くことを撮影で確認してから**仕様書に貼る（見た目だけ作って動作未確認のまま貼らない）
   - 既存画面の「変更前の挙動」もモックで示したい場合（例: 現状はクリックしても何のフィードバックも無い）は、`Before.dc.html`と`Main.dc.html`の2artboardを`canvas.json`で横に並べる。`Main.dc.html`の名前は変えず、表示上の見出しは`"title": "After"`で上書きする。この場合でも実ページのbefore画像（手順2）は別途撮る（モックBeforeは実物の代わりにならない）
   - 一覧の各行を独立して操作できるモックでは、状態を単一の`phase`変数で持たない（1行しか動かなくなる。行ごとの状態オブジェクトを返す）
4. **画像をコミットする**: before/after画像（状態ごとの画像を含む）を`docs/spec/<機能名>/assets/`配下にコミットする（会話内共有のみでは残らないため）
5. **仕様書ファイル`docs/spec/<機能名>/SPEC.md`を次のテンプレートで書く**（セクションの意味は下記参照）:

```markdown
## UI案

### 現状 (対象パス、例: app/orders/page.tsx)
![現状の説明](./assets/xxx-before.png)

### 変更後 (対象パス、例: app/orders/page.tsx)
![変更後の説明](./assets/xxx-after.png)

### コード調査で分かったこと
- (呼び出すServer Action/RPC、成功後の再取得有無、エラー時の挙動など)

## UI受入条件

- (配置・導線・文言について、開発者の意図を反映した箇条書き)

## 状態設計

| 状態 | 見せるもの | 画像(モックで再現した状態のみ) |
|---|---|---|
| 通常 | | ![](./assets/xxx-after-idle.png) |
| 処理中 | | ![](./assets/xxx-after-processing.png) |
| 成功 | | ![](./assets/xxx-after-done.png) |
| エラー | | |
| 権限なし | | (モック対象外なら空欄) |
| 空 | | |

## 業務・認可

- (誰が操作できるか、冪等性など)

## 選ぶテスト

- UI: 
- RLS: 
- RPC統合: 
- E2E: 
```

- **UI受入条件**：配置・導線・文言など、開発者の好みが出る部分を明記する
- **状態設計**：通常状態の見た目だけでなく、「操作・失敗・権限・データなしの時」を軽く決めておく。これが無いと「連打されたら？」「保存に失敗したら？」「0件なら？」「非管理者が直接開いたら？」が未決定のまま実装に入り、AIが勝手に曖昧なUXを作ってしまう。主要画面には最低限この6状態を書く。インタラクティブモックで再現した状態は「画像」列に`mock-capture.js`で撮った画像を貼る（権限なし・通信失敗などモックで再現しない状態は空欄でよい。全状態の画像を無理に作らない）
- **選ぶテスト**：[品質ループと昇格基準](../../../docs/agents/quality-loop.md)・`docs/agents/layer-test-selection.md`の`TEST_TYPES`キーと対応させる。ここで書いたテスト種別は、実装時に`aidd-phase2`ワークフローの`specTests`引数へそのまま渡す

ロジック・データ・DB・API層が含まれる場合は、UI受入条件の代わりに「変更する箇所／変更しない箇所」を明記する。既存の挙動・権限・エラーハンドリングのうち維持されるものも書く（変更点だけ書くと、書いていない部分は変更しない、という前提が伝わらない）。状態設計・選ぶテストのセクションは共通で使う。

**`design`スキルでのモック作成はUI層を含む限り省略不可**（開発者への確認も不要——確認すると「お任せ」で省略側に流れやすいことが実際のテストで判明したため、無条件で作る）。ボタンの配置・余白・階層関係は文章では再現性を保てず、実装時にAIが勝手に決めてしまう。「既存パターンの流用だから新規モックは不要」という自己判断もしない（既存パターンをどう当てはめるかという配置自体が、モックで確認すべき対象）。

状態設計・選ぶテスト等、モック作成以外の一部セクションの記載を軽微な変更で省略したい場合は、省略してよいか開発者に明示的に確認する。開発者の返答が「特にない」「お任せ」等で選好不明な場合は、**省略しない側を選ぶ**。

**提示前のセルフチェック（UI層を含む場合）**。次のいずれかに該当したら、提示せずに先に直す:
- UI変更があるのに「UI案」がモック無しの文章だけになっていないか
- 既存画面の変更なのに、before画像が無くafterだけになっていないか
- クリックで状態が変わる作りのモックなのに、`mock-capture.js`で実際に動かして撮った画像が無い（＝動作未確認のまま貼っている）状態になっていないか
- 複数artboardを撮った場合、`artboardIndex`の指定と撮れた画像の中身が一致しているか目視で確認したか

`SPEC.md`を提示した上で、「この内容で実装に進んでよいか」という、内容の当否とは別の実装可否そのものへの確認を取る。この確認は内容確認用の質問（ステップA）や個々の選択式回答と兼用しない。明示的な承認が得られてから、Role 4に進む。

### Role 4: Implementer（実装・検証）

**影響層が2つ以上ならPhase2ワークフローを使う**: Role 3で選ばれた層が2つ以上の場合、手動実装ではなく`aidd-phase2`ワークフロー（`Workflow`ツール、`scriptPath: ".claude/workflows/aidd-phase2.js"`）を呼び、`args: { taskDescription, layers: [選ばれた層] }`で並列実装（implementer-ui/data/db → integrator → 4観点レビュー）させる。返り値が`aidd-phase2-blocked`ならその内容をそのままCriticに引き継ぎ、人間に報告してから再検討する。影響層が1つだけなら以下の手動フローでよい（並列オーケストレーションのオーバーヘッドに見合わないため）。

**手動実装フロー（影響層1つの場合、またはPhase2が使えない場合）:**
1. 既存コードのパターン・命名・設計を踏襲して実装する
2. `npm run build` と `npm test` を通す
3. ブラウザプレビューで実際に動作確認する。riff-gearでの定石:
   - `preview_start`でdevサーバー起動（Bashで直接起動しない）
   - ログインが要る場合はMailpit(`http://127.0.0.1:54524`)からマジックリンクを取得する
   - テストデータが要る場合はSupabase REST API(`curl -X PATCH .../rest/v1/products?...`)で一時的に調整する
   - 通知系など画面に出ないロジックは`console.log`の一時デバッグ出力で確認する

**DBマイグレーションを1つでも追加したら、聞かずに必ずロールバックSQLを書く**（コストが10分程度と低く、判定するまでもなく常に必須のため）。マイグレーションファイル末尾に`-- ROLLBACK:`コメントブロックとして追加後の逆操作（`drop policy`/`drop function`/`alter table ... drop column`等）を書き、`supabase db reset`で通常適用が通ることを確認する。ロールバック自体を別途適用して巻き戻ることまでは必須にしない（履歴が汚れるため）が、SQL自体は目視で「対応関係が正しいか」を確認する。

**Phase2ワークフローを使った場合も**、Role 5のCriticチェックリストは省略しない（integratorのbuild/test確認を鵜呑みにせず、最終的な`git diff`確認は必ず人間相当の目で行う）。ロールバックSQLの要否もPhase2内のdb実装エージェントに同様に指示する。

**UI変更を検知したらpr-screenshotスキルの使用を確認する**: `aidd-phase2`の返り値(`result.uiChange`)は`changedFiles`のパスから`app/**/page.tsx`の変更を機械判定している(推測ではない)。`uiChange.uiChanged`が`true`なら、`uiChange.pagePaths`(App Router規約で変換したURLパス候補)を添えて「UI変更を検知しました。`pr-screenshot`スキルでPR用スクリーンショットを撮りますか？」と開発者に確認する。手動実装フロー(影響層1つ)でUIを変更した場合も同様に確認する(この場合は`app/`配下の`.tsx`を変更したかどうかで自分で判定する)。**撮る場合はbefore(変更前)とafter(変更後)の両方を撮る(after1枚だけで済ませない。詳細は`pr-screenshot`スキルの「UI差分があるPRはbefore/after両方が必須」を参照)。**

### Role 5: Critic（検証・批判）

Implementerの「動いた」を疑う。まず検証範囲をAskUserQuestionで確認してから、基本チェックリストを実施する。

**この判定は機能（PR）単位で1回だけ行う**。Phase2ワークフロー内でintegrator/reviewerが差し戻し→再実装を繰り返しても、そのイテレーションごとに聞き直さない。差し戻しは実装品質の収束プロセスであり、リスク判定のやり直しではない。

**検証範囲の確認（AskUserQuestion, multiSelect）**

「このPRは次のどれに該当しますか？」を開発者に聞く。選択肢:
- RLSポリシー・認可(auth)ロジックの変更を含む
- 過去に実害（本番障害・データ不整合・在庫や決済のバグ）があった領域に触れる
- 上記のいずれにも該当しない軽微な変更

（DBマイグレーションを含むかどうかはRole 4で既に判定済み・対応済みなのでここでは聞かない）

回答に応じて追加で必須になる項目:
- **RLS/認可を含む** → API直叩き・RLS直叩き（anon/authenticated/service_roleそれぞれでcurl等を使い直接検証）を必須にする。さらに、**curlで検証したシナリオを`tests/rls/`または`tests/rpc/`の自動テストとして追加するまでを完了条件とする**（手動検証は「今日壊れていない」しか保証しない。将来のマイグレーション・ポリシー変更での回帰はCIのテストだけが検知できる。実例: PR #83のtests/rpc/sales-dashboard.test.ts）
- **過去に実害があった領域** → Fault Injection（意図的な状態不整合・競合状態を注入するテスト）が要るか開発者に確認する（機能規模に対してオーバースペックなら不要と伝えてよい）
- **該当なし** → 下記の基本チェックリスト＋通常のE2E（ブラウザ手動確認）のみでよい

このRole終了時、実施した検証は「E2E／API直叩き／RLS／認可直叩き／Fault Injection／復旧手順」を軸に、項目ごとに `✅ 完了／🟡 一部完了／⬜ 未実施／➖ 対象外` の4値で開発者に報告する（一括りに「検証済みです」と言わない。`⬜ 未実施`・`➖ 対象外`には理由を必ず添える。「失敗」と「やらない判断」を区別できない○/△/✗は使わない）。復旧手順はRole 4で対応済みなら自動的に`✅ 完了`になる。この4値(絵文字付き)は`.github/PULL_REQUEST_TEMPLATE.md`の検証表と同じ語彙であり、ここでの報告がそのままRole 6でPR本文に転記される。

**証跡の書き方（曖昧な「完了」を避けるため。PR #119のレビューで判明）:**
- E2Eが手動確認（実ブラウザでの目視操作）なら証跡欄に`(手動)`と明記する。自動E2Eテストと誤解されないため
- 復旧手順は「ロールバックSQL/手順を記載した」と「実際に適用して巻き戻り確認した」を書き分ける。記載のみでも`完了`扱いにしてよい（[[project_migration_rollback_convention]]）が、証跡欄には未実証である旨を書く
- DBマイグレーションを含む場合、検証表に`Migration適用`の行を追加し、`supabase db reset`等で適用自体が通ることを確認したと明記する
- Fault Injectionを`対象外`にする場合、「オーバースペック」で終わらせず、「外部副作用なし」「複数テーブルの原子更新なし」「再送で状態が変わらない（冪等）」等、テスト選択の機械判定基準([[project_layer_test_review_design]])とそのまま繋がる具体的な理由を書く
- 「変更した層」でRLS/認可にチェックする場合、実装が`security definer`/`security invoker`のどちらかを書き添える（PR本文の他箇所と食い違わせない）
- 「残る仕様上の制約」欄は、未解決の仕様上の制約と、`aidd-phase2`のテスト選択機構で「基盤未整備」扱いのため今回未実施のテスト（fail要因にはならない推奨扱い）を分けて書く

**基本チェックリスト（毎回）:**

- [ ] 一時デバッグ出力(`console.log`等)を削除したか（`git diff`で確認）
- [ ] テストデータ（在庫数・テスト注文・テストユーザー）を元に戻したか
- [ ] プレビューサーバーを停止したか
- [ ] `git diff`の内容が意図した変更だけか（無関係ファイルの混入がないか）
- [ ] 削除・復元後にもう一度 `npm test` が通るか

### Role 6: Closer（完了処理）

1. 変更ファイルを個別に `git add`（`git add -A` は使わない）してコミット。イシューがあればコミットメッセージまたはPR本文に `closes #N` を入れる
2. push → `gh pr create`。PR本文は`.github/PULL_REQUEST_TEMPLATE.md`の3欄（変更した層／実施した検証／残る仕様上の制約）を**必ず全て埋める**。検証表はRole 5の4値報告をそのまま転記する。「残る仕様上の制約」は空欄禁止で、制約が無ければ`なし（確認済み）`と明記し、あれば「制約／影響／受容判断または再検討条件」を1件ずつ書く（コードコメントや会話に散らばった既知の制約をPR単体で復元できるようにするため）。UI差分のbefore/after画像を貼る場合、見出しに対象パスを明記する（例: `### 変更前 (app/orders/page.tsx)`）。画像自体にページ名バナーは焼き込まない（`pr-screenshot`スキル参照）。画像の埋め込みはリポジトリコミット+`raw.githubusercontent.com`形式の絶対URLを使う（相対パスはPR本文でレンダリングされない、[[known-failure-patterns.md]]参照）
3. `gh pr checks --watch` でCI全通過を確認する
4. **マージは開発者に確認してから** `gh pr merge`
5. マージ後: リモートブランチ削除、イシューのクローズ確認、メモリ(`MEMORY.md`)に残すべき決定があれば更新
6. **学びの置き場判定**: この機能の作業中に発生した障害・CI失敗・レビュー指摘・ハマりを振り返り、それぞれ「どこに留めるか」を1行決める（テスト／スキル・テンプレート／known-failure-patterns.md／implementation-patterns.md／どこにも留めない）。判断基準と選択肢の詳細は[品質ループと昇格基準](../../../docs/agents/quality-loop.md)を正本とする。何も発生しなかった場合はスキップしてよい
